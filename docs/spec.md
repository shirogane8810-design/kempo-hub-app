## 1. 概要と前提

日本拳法の大会を、申込から結果公開まで一つのサイトで回す「大会ハブ」を、運用費0円で作る。12月の全国新人戦で最小版（MVP）を実戦投入し、来年の総合選手権までに全機能をそろえる。

目的

- 運営の手作業（申込集計、組合せ、時間割、結果まとめ）をなくす
- 観客と選手が、自分の見たい試合を最後まで追える（決勝まで人が残らない問題への対策）
- 協賛企業に広告効果を数字で見せる。賛助会員（事業A）と運営パッケージ（事業C）の土台にする

利用者

| 利用者 | 主な使い方 | 端末 |
| --- | --- | --- |
| 運営（NIKKEN NEXT・大会主催者） | 大会作成、エントリー管理、組合せ、時間割、当日進行、広告管理 | PC |
| 大学・道場の代表 | 所属選手の登録、エントリー、団体戦オーダー提出 | PC・スマホ |
| 選手 | プロフィール、戦績、出番通知、受付 | スマホ |
| 審判 | 担当コートの採点、結果の確定 | タブレット |
| 観客・ファン | トーナメント表、コート別の進行、選手フォロー、配信 | スマホ |
| 協賛企業 | 広告の表示・クリック数の確認 | PC |

前提

- 決済は扱わない。参加費や会費は振込で受け、サイトでは「入金済み」の印だけ管理する
- サーバー・データベース・通知はすべて無料枠で運用する。独自ドメインを取る場合だけ年額の費用がかかる（任意）
- 開発は Claude Code と Codex に実装させ、人間は仕様決め・確認・リリース判断に集中する
- Smoothcomp から借りるのは機能の考え方だけで、コードとデザインは独自に作る

## 2. システム全体図

画面は Cloudflare Pages で配信し、データ・ログイン・通知などの処理は Supabase にまとめる。

```
[運営PC] [大学代表・選手] [審判タブレット] [観客スマホ] [協賛企業]
                         │
                         ▼
     Cloudflare Pages：Webアプリ（PWA, React + TypeScript）
       ├ 公開サイト（大会・トーナメント表・結果・コート別進行・選手フォロー）
       ├ 管理画面（運営・大学代表）
       └ 審判画面（PINで入る・採点・結果確定・オフライン継続）
            │ 観客：30秒ごとに live_snapshots を取得
            │ 審判・運営：リアルタイム同期
            ▼
     Supabase（無料プラン、本番用と開発用の2プロジェクト）
       データベース(PostgreSQL+RLS) / ログイン(Google・メール・匿名) /
       リアルタイム(審判・運営・大学代表のみ) / サーバー処理(Edge Functions) / ファイル保管
            │
            ├ Web Push（出番・結果の通知）
            └ YouTube Live（配信を公開サイトに埋め込み）

開発：Claude Code・Codex → GitHub（コード・自動テスト・毎日のバックアップ・休止防止）
      → マージで Cloudflare Pages と Supabase に反映
```

使う技術

| 用途 | 技術 | 選んだ理由 |
| --- | --- | --- |
| 言語 | TypeScript | 画面とサーバー処理を同じ言語で書ける |
| 画面 | React + Vite、Tailwind CSS | 学生が引き継いでも情報が多く、画面だけの配信で済む |
| アプリ化 | PWA | アプリストアの審査も登録費も不要 |
| データ・ログイン・処理 | Supabase | 1つのサービスで全部そろう |
| 多言語 | i18next | 日本語と英語の切り替え |
| テスト | Vitest、Playwright | 計算と画面の操作を自動で確かめる |
| コード管理・自動化 | GitHub、GitHub Actions | 自動テスト、バックアップ、休止防止 |

## 6. データ設計

実装: `supabase/migrations/20261003000000_p1_core.sql`（P1 分）。全テーブルに `organization_id` を持たせ、P4 で他団体に提供するときに作り直さなくて済むようにする。

試合の結果は「採点記録（match_events）」を正とする。本数や勝者は記録から計算するので（`src/lib/scoring.ts`）、取り消しや修正の履歴が必ず残り、オフラインからの同期も順番に積むだけで済む。

### 6-1. 大会と試合

| テーブル | 中身 | 主な項目 | つながり |
| --- | --- | --- | --- |
| organizations | 主催団体 | 名前、種別 | 大会を複数持つ |
| events | 大会 | 名前、日程、会場、申込期間、公開状態、要項PDF、通知のN試合前 | 主催団体に属する |
| rule_sets | ルールセット | 勝ちに必要な本数、試合時間、延長の時間、反則の扱い | 部門が参照する |
| divisions | 部門 | 個人／団体、男女・段級などの条件、団体の人数 | 大会に属し、ルールセットを使う |
| courts | コート | 名前、配信URL | 大会に属する |
| court_secrets | 審判用PIN | PINのハッシュ、失敗回数、ロック期限 | コートに1つ。画面からは読めない |
| court_grants | 採点権 | 端末（匿名ログイン）、期限 | コート×端末 |
| brackets | トーナメント | 形式、乱数シード、確定ロック | 部門に1つ |
| matches | 試合 | 回戦、枠番号、赤・白の出場者、勝者、勝ち上がり先、コート、予定時刻、状態 | トーナメントに属し、次の試合を指す |
| match_events | 採点記録 | 種類（開始、停止、本、反則、判定、不戦勝、取り消し、確定）、赤白、時刻、端末 | 試合に属する。追記のみ |
| live_snapshots | 公開用の進行データ | 大会ごとの「今の状態」をまとめた軽いデータ | 大会に1つ |

## 7. 権限とセキュリティ

権限は画面ではなくデータベース自体（RLS）で守る。テスト: `supabase/tests/rls.test.sql`。

| 役割 | できること | できないこと |
| --- | --- | --- |
| システム管理者（NIKKEN NEXT） | すべて。主催団体の追加と管理者の任命 | ― |
| 主催団体の管理者（org_admin） | 自団体の大会・部門・組合せ・審判・広告の管理、結果の修正 | 他団体のデータに触る |
| 当日スタッフ（staff） | 受付、進行管理、試合のコート付け替え | 大会設定の変更 |
| 大学・道場の代表 | 自分の所属の選手登録、エントリー、入金報告 | 他校のデータに触る、締切後の変更、入金確認の書き換え |
| 選手 | 自分のプロフィールと公開範囲、自分の受付QR | 他の選手の非公開情報を見る |
| 審判（PINで入る） | 担当コートの試合の採点と確定 | 他のコートの採点、確定後の修正、採点記録の書き換え |
| 協賛企業（専用リンク） | 自社の広告実績の閲覧 | それ以外すべて |
| 一般の閲覧者 | 公開中の大会情報、公開された選手情報の閲覧、端末でのフォロー | 書き込み全般 |

決まりごと

- 個人情報は必要な分だけ持つ。住所、生年月日、電話番号は持たない
- 選手の写真と学年は初期設定で非公開にし、本人が公開を選んだものだけ出す
- 審判のPINはハッシュにして保存し、大会ごとに作り直す。間違いが続いたら一時的に入力を止める
- 結果の修正、権限の変更、データの削除はすべて操作履歴に残す
- 管理用の秘密鍵は画面側のコードには絶対に入れず、サーバー側の処理と GitHub の秘密設定にだけ置く
- 登録時にプライバシーポリシーと利用規約への同意を取る。内容は公開前に詳しい人に確認してもらう

## 8. 非機能要件・運用・引き継ぎ

観客向けの画面はリアルタイム接続を使わず、30秒ごとに `live_snapshots` を取りに行く形にして無料枠に収める。

| サービス | 無料枠の上限 | 対策 |
| --- | --- | --- |
| Supabase データベース | 500 MB、無料プロジェクトは2つまで | 本番と開発の2つで使う。写真はファイル保管に置く |
| Supabase ファイル保管 | 1 GB | 写真はアップロード時に縮小。広告画像も容量を決める |
| Supabase 通信量 | 月 5 GB | 観客は30秒ごとの取得。画面を開いていないときは取得しない |
| Supabase リアルタイム | 同時接続 200、月 200万メッセージ | 審判・運営・大学代表だけが使う |
| Supabase Edge Functions | 月 50万回 | 通知の送信、組合せの生成、結果確定、PIN確認だけに使う |
| Supabase の休止 | 1週間使われないとプロジェクトが止まる | GitHub Actions で毎日アクセス（`.github/workflows/keepalive.yml`） |
| Cloudflare Pages | 月 500 回までビルド、1サイト2万ファイルまで | 十分に収まる |

Vercel の無料プランは個人の非営利利用に限られ、広告を載せるサイトは対象外なので使わない。

大会当日の通信量の試算: 観客300人 × 1時間120回 × 8時間 × 8 KB ≒ 2.3 GB。1か月に大会が2日あると危ない。その場合は独自ドメイン＋Cloudflare のキャッシュか、その月だけ有料プランにする。新人戦の前に実データで試算し直す。

会場での備え

- 審判の端末は会場の Wi-Fi ではなくスマホ回線（テザリング）を基本にする
- 通信が切れても採点は続けられる（REF-05）。それでも紙のトーナメント表と採点用紙を必ず用意する
- 前日に全端末でログインと採点を試す。当日は運営PCで1人が進行管理画面を見張る

保守

- 無料プランには自動バックアップがないので、GitHub Actions で毎日データを書き出し、非公開の場所に保管する
- PR ごとに確認用の URL が発行され、確認してマージすると本番に反映される
- 大会の3日前から大会後までは、新機能を本番に入れない（不具合の修正だけ）

引き継ぎ

- GitHub、Supabase、Cloudflare のアカウントは個人名義にせず、NIKKEN NEXT の共有メールで作る「組織」にする
- 管理者は常に2人以上置き、1人は後輩にする
- 残す文書: この仕様書、README、運用マニュアル（大会の作り方）、当日マニュアル（審判・受付向け）
- AI向けのルールブック（CLAUDE.md と AGENTS.md）があるので、プログラミングに詳しくない後輩でも AI で改修できる
